# WiFi-NAG V1.0.5 BLE Obstacle Shift Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 WiFi-NAG V1.0.5 中接收 T2CAN 的权威 BrakeState，并在严格安全门和锁存状态机控制下，基于每一帧实时 `0x118` 注入最长 500 ms 的虚拟 P 挡帧，同时完成 BLE/障碍物换挡独立大卡片。

**Architecture:** BLE 任务只校验消息并把不可变 BrakeState 快照发布到无锁邮箱；CAN 任务读取快照、推进纯状态机并独占虚拟 P 帧发送。基础 NAG 仍只过滤 `0x370`，BLE 初始化后的精确白名单统一为 `0x370/0x255/0x12B/0x118`；WebUI 只读取诊断快照和更新持久化开关。

**Tech Stack:** C++17、ESP-IDF 6.x/Arduino compatibility、ESP32-S3 TWAI、NimBLE、PlatformIO native + Unity、Python unittest、静态 HTML/CSS/JavaScript、NVS Preferences。

## Global Constraints

- 实施工作只在 `V1.0.5` 隔离分支和 `C:\Users\wxy\Desktop\WIFI-NGA\.worktrees\V1.0.5` 中进行。
- 本计划只实现 WiFi-NAG 仓库；T2CAN 必须按设计规格发送 `MSG_BRAKE_STATE=0x12`，不在本仓库伪造 T2CAN 数据源。
- BLE 基础包保持 20 字节、Magic `0xA7`、协议版本 `0x02`、10 字节 Payload、CRC16-CCITT。
- `kRequiredCaps=0x0F`，`kAdvertisedCaps=0x1F`；缺少能力 `0x10` 只能禁用障碍物换挡，不能破坏旧 BLE 功能。
- BrakeState 新鲜度为 200 ms，本机 `0x118` 新鲜度为 50 ms，虚拟 P 窗口最长 500 ms。
- 功能开关首次启动默认开启并写入/读取 NVS；启动状态始终是 `WAIT_RELEASE`。
- `0x118` 只随 BLE 功能加入有效过滤器；未编译 BLE 时基础 NAG 过滤器仍只有 `0x370`。
- 当前硬件是单路 TWAI；实现是同总线注入虚拟 P，不能声称物理拦截或删除原车真实 `0x118`。
- 虚拟 P 只修改 Byte2=`0x32`、Byte6=`0x00`，保留 Byte1/3/4/5/7，并按 `Byte0=(Byte1+Byte2+Byte3+Byte4+Byte5+Byte6+Byte7+0x19)&0xFF` 重算校验。
- 不允许固定帧重放、缓存帧补发、结束时恢复帧或 BLE 回调直接调用 CAN `send()`。
- CAN Write、CAN 在线、非 OTA/重启准备是发送硬门；任一不满足立即停止且不自动解锁。
- UI 源文件修改后必须重新生成 `include/web/mcp2515_dashboard_ui.base.h`，并通过 `scripts/minify_dashboard.py --check`。

- [ ] **Step 6: Implement pure mutation and state transitions**

Use this checksum implementation:

```cpp
static uint8_t checksum118(const CanFrame &frame)
{
    uint16_t sum = 0x19U;
    for (uint8_t index = 1; index < 8; ++index)
        sum = static_cast<uint16_t>(sum + frame.data[index]);
    return static_cast<uint8_t>(sum & 0xFFU);
}
```

Transition rules must be encoded in this order on every `tick()`:

```text
session changed / link not ready / invalid mailbox → WAIT_RELEASE
capability absent → WAIT_RELEASE
feature or CAN Write disabled → stop and require release
BrakeState missing or age > 200 ms → WAIT_RELEASE
ACTIVE 中最后真实 0x118 age > 50 ms → WAIT_RELEASE
fresh brakePressed=0 + releaseConfirmed=1 → ARMED
fresh brakePressed=0 + releaseConfirmed=0 while ACTIVE → LATCHED
ACTIVE window age >= 500 ms → LATCHED
```

Only `observeFrame()` may call `driver.send()`. It must first run `tick()`, reject non-standard `0x118`/DLC 8 violations, ignore its own last-sent fingerprint, store the true frame and gear, then either send the next ACTIVE frame or start a new window from ARMED. On send failure, enter `LATCHED` with `SHIFT_REASON_TX_FAILED` and never retry during the same press.

## Device Validation Handoff

Automated tests and a successful build do not prove that a target ECU will prefer the injected P frame over the original D/R frame on a single CAN bus. After code review, provide firmware only for controlled bench or closed-area validation with CAN capture. The capture must show real and injected `0x118`, counter continuity, checksum validity, exact 500 ms maximum window, immediate safety exits, single-trigger latch and confirmed-release rearm before V1.0.5 can be considered behaviorally validated.
