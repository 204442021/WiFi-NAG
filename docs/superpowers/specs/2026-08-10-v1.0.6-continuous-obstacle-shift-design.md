# V1.0.6 条件驱动持续虚拟 P 设计

## 1. 背景与根因

当前 V1.0.6 障碍物换挡控制器使用一次性 1000 ms 窗口，并要求在自动触发前先收到一帧“新鲜且明确释放”的 T2CAN BrakeState。窗口结束后控制器锁存，必须再次看到新鲜释放才能重新就绪。

实际 T2CAN 在物理刹车未踩下时不会持续刷新 BrakeState。最近一次释放状态因此会自然超过 WiFi-NGA 的 500 ms 控制快照年龄上限。旧控制器把这个正常的空闲超时解释为不能解锁，持续停留在“等待释放”，后续操作表现为锁死；手动入口也因为共用快照新鲜度检查而显示“刹车数据超时”。

本次修改只作用于 WiFi-NGA 的 `V1.0.6` 隔离分支，不修改 T2CAN-B。BrakeState 线值 0..11 的协议兼容修复继续保留。

## 2. 已确认目标

- 删除自动路径的 1000 ms 注入窗口。
- 删除“先看到新鲜释放才能解锁”的状态与锁存。
- 删除手动虚拟 P 按钮、POST 接口、请求 mailbox 和相关诊断字段。
- 保留 T2CAN 真实挡位 D/R 门槛。
- 保留 T2CAN 车速有效且车辆静止门槛。
- 只使用 T2CAN 的物理刹车状态；物理刹车有效且踩下时才允许自动注入。
- 安全条件持续成立时，对每帧有效的真实 `0x118` 最多发送一帧对应的虚拟 P。
- 任一安全条件失效时立即停止，不缓存、不补发、不定时重放历史帧。
- 版本号保持 `V1.0.6`，完成后使用 D 盘现有 PlatformIO 工具链及缓存编译，重新生成 OTA 和 16 MB 线刷固件，并推送远端 `V1.0.6` 分支。

该功能仍只用于台架或封闭场地验证。单路 TWAI 无法拦截原车帧，因此真实 `0x118` 与注入的虚拟 P 帧会在同一总线上共存。

## 3. 方案选择

采用方案 2：把控制器改为条件驱动的两态模型。

不采用在旧状态机上旁路窗口的最小补丁。保留 `WAIT_RELEASE`、`ARMED`、`LATCHED`、窗口计时和手动触发字段会形成不可达或语义矛盾的状态，增加后续再次锁死的风险。

新模型只有：

- `IDLE`：当前不满足全部安全门，或尚未收到可作为模板的真实 `0x118`。
- `ACTIVE_P`：全部安全门成立；每收到一帧合格的真实 `0x118` 就尝试发送对应的虚拟 P。

`ACTIVE_P` 不是一个独立计时窗口。它完全由当前输入条件决定，可以持续超过 1000 ms，也可在任一条件失效时立即回到 `IDLE`。

## 4. 安全门

每次控制器 tick 和每次处理真实 `0x118` 时，都重新检查下列条件：

| 条件 | 要求 |
|---|---|
| 功能开关 | 障碍物换挡功能已开启 |
| BLE/T2CAN 会话 | 已连接、握手能力有效、BrakeState 控制快照存在 |
| 快照年龄 | 本地接收年龄不超过现有 500 ms 上限 |
| 物理刹车 | `physicalKnown && physicalFresh && physicalPressed` |
| 车辆静止 | `speedFresh && stationaryConfirmed` |
| 真实挡位 | `gearFresh` 且 `realGear` 为 D 或 R |
| CAN 写入 | 状态已知且已开启，CAN 在线 |
| 系统状态 | 非 OTA、非重启准备状态 |
| 模板帧 | 标准数据帧、ID `0x118`、DLC 8、现有校验合法、不是本机注入回环 |

本机 `0x118 Byte2` 不参与真实挡位判断；T2CAN BrakeState 中的 `realGear` 是挡位权威。生成虚拟 P 时仍复制刚收到的真实帧，写入 Byte2=`0x32`、Byte6=`0x00`，然后重算 Byte0 校验和。

## 5. 空闲超时与解除锁死

空闲时最近一次“已释放”BrakeState 变旧属于正常状态：

- 控制器显示等待物理刹车，不进入锁存。
- 不要求用新鲜释放帧预先解锁或预先武装。
- 下一次收到新鲜的物理刹车踩下 BrakeState 后，只要 D/R、静止和技术门同时有效，就立即进入 `ACTIVE_P`。
- 若“踩下”状态本身超过 500 ms，则立即停止注入；只有后续新鲜状态才能恢复。

因此，松刹车状态超时不会阻止下一次踩刹车触发，同时也不会把过期的“踩下”状态长期当真。

## 6. 持续发送与停止语义

当全部安全门成立时：

1. CAN 任务收到一帧新的真实 `0x118`。
2. 排除与本机最近发送虚拟帧匹配的回环。
3. 验证帧结构与校验。
4. 再次检查当前安全门。
5. 从当前真实帧生成一帧虚拟 P，并立即尝试发送一次。

每帧真实 `0x118` 最多对应一次发送尝试。控制器不保存待重试帧，不按固定周期自行生成帧，也不补发历史帧。

下列任一情况发生时停止注入并回到 `IDLE`：

- 物理刹车明确释放、未知或过期；
- 车速未知、过期或车辆不再静止；
- T2CAN 挡位离开 D/R，包括 P、N、未知或过期；
- BrakeState 控制快照超过 500 ms；
- BLE/T2CAN 会话或能力失效；
- CAN Write 关闭或状态未知；
- CAN 离线；
- OTA 开始或设备准备重启；
- 功能开关关闭。

单帧 CAN 发送失败只记录失败且不重放该帧。若下一帧真实 `0x118` 到来时全部安全门仍成立，允许对下一帧重新尝试发送；不因为一次 TX 失败形成永久锁存。

## 7. 删除的手动链路

完整删除下列内容，而不是仅隐藏按钮：

- WebUI 的“手动虚拟 P（1 秒）”按钮、就绪文案和请求脚本；
- `/ble_shift_manual` POST 路由；
- BLE bridge client 中的手动请求 generation/mailbox；
- `ObstacleShiftRuntimeInputs` 中的手动请求输入；
- 控制器中的手动触发源、手动窗口计数、手动就绪和拒绝原因；
- `/ble_status` 中只为手动入口或窗口服务的字段；
- 自动/手动窗口计数及剩余窗口时间等不再成立的 UI 诊断。

与页面主题 `manual` 模式等无关的同名代码不得误删。

## 8. 状态与诊断

WebUI 障碍物换挡卡片改为反映条件驱动语义：

- 状态机：`等待条件` / `持续注入 P`。
- 物理刹车：踩下、释放或无效，并显示快照年龄。
- T2CAN 挡位：真实挡位与新鲜度。
- 车辆状态：车速与静止确认。
- `0x118`：实时模板有效性与年龄。
- 虚拟 P：正在随真实帧发送或未发送，不再显示剩余毫秒数。
- 原因：显示当前第一个阻断安全门；空闲释放过期应描述为“等待踩刹车/刹车数据超时”，不得显示锁存或等待释放。
- 计数：真实 `0x118` 接收数、虚拟 P 成功/失败数、进入持续注入的次数、BrakeState 非法数和序列统计。

为避免外部页面误解，旧的窗口、锁存、触发来源和手动就绪 JSON 字段应从生产者及本项目消费者同步删除。若某个通用诊断字段有其他调用者，则保留字段名但改为明确的非窗口语义，并在回归测试中固定行为。

## 9. 测试策略

先修改测试使其表达新需求并确认在旧实现上失败，再修改生产代码。

### 9.1 Native 控制器测试

- 松刹车快照变旧后保持 `IDLE`，不锁存；下一帧新鲜踩下可直接激活。
- D/R + 静止 + 新鲜物理刹车踩下可激活，无需先看到释放。
- 条件持续超过 1000 ms 后仍对新的真实 `0x118` 发送虚拟 P。
- 每帧真实 `0x118` 最多一次发送尝试，不补发、不重放。
- 物理刹车释放或踩下状态过期立即停止。
- 车辆移动、车速过期、挡位 P/N/未知/过期立即停止。
- CAN Write、CAN 在线、BLE 会话、OTA 和重启门继续有效。
- 本机回环、错误 ID/DLC/校验不能触发发送。
- 单帧发送失败不重放；下一帧在安全门仍成立时可重试。

### 9.2 Python 回归测试

- 源码中不再存在 1000 ms 窗口常量、自动锁存和等待释放路径。
- `/ble_shift_manual`、手动请求 mailbox、按钮和脚本全部移除。
- 源 UI、生成的 gzip UI 与服务端状态字段保持同步。
- BrakeState 原因码 0..11 兼容修复保持不变。
- `VERSION`、WebUI/固件信息及 `APP_VERSION` 仍为 `V1.0.6`。
