# WIFI-NAG V1.0.3 CAN 架构重建设计

## 1. 目标与边界

本设计基于 `V1.0.3`，基线 SHA：`760744655191998239cc8447732e9fe4e2d889c8`。

本次只重建 WIFI-NAG 的底层 CAN 架构，不新增车辆控制功能，不改变现有 Nag 对外行为，不改 WiFi/DNS/NAPT/WebUI 的产品功能，不改变 OTA 分区与发布流程。

核心目标：

1. 将 CAN 实时链路统一为单一、可验证、可回退的数据流。
2. 将安全控制、实时业务、普通控制、低优先级发送分层。
3. 让 CAN 实时任务独占 TWAI，禁止业务 handler 和 WebUI 直接操作驱动。
4. 将“业务生成成功、TWAI 入队成功、总线发送结果”分离统计。
5. 建立统一的状态机处理启动、输入超时、Bus-Off、OTA、重启和恢复。
6. 保留 V1.0.3 已有的 Listen Only、安全重启、TX recessive、Bus-Off 冷却恢复和 Nag 算法。

## 2. 当前架构结论

V1.0.3 当前使用 ESP32-S3 原生 TWAI，500 kbit/s，仅监听并处理 `0x370 / 880`。CAN 实时任务固定在 Core 0，WiFi/lwIP 主要运行在 Core 1。

当前链路：

`TWAI RX → TWAIDriver::read → appLoop → NagHandler::handleMessage → 直接 driver.send → twai_transmit`

主要问题：

- `NagHandler` 同时负责协议、业务、统计和发送，无法建立统一 TX 调度。
- `twai_transmit()` 成功只代表进入 TWAI 发送队列，不能等同总线发送完成。
- `framesSent` / `nagEchoCount` 在底层发送结果明确前就被更新。
- Web/CAN 存在普通全局变量跨核共享，实时状态边界不清晰。
- 输入只检查 ID、DLC 和简单自发帧识别，缺少 checksum、counter、新鲜度、连续有效帧确认。
- Bus-Off、OTA、restart、write enable、driver failure 分散处理，没有统一 Supervisor 状态机。
- TX 硬件队列较深，未来加入多优先级功能时可能形成优先级倒置。

## 3. 选定架构

采用“单 CAN 实时任务 + 统一流水线 + 软件 TX 调度器 + Supervisor 状态机”。

不采用：

- 只拆文件但保留 handler 直接发送：无法解决核心实时问题。
- RX/业务/TX 三任务拆分：当前单 TWAI、单核心业务场景下增加队列延迟和同步复杂度，收益不足。

### 3.1 运行模型

Core 0：

- `can_rt`：高优先级，独占 TWAI，完成 RX、验证、业务处理、TX 调度、发送结果与恢复状态机。

Core 1：

- WiFi / lwIP / HTTP / DNS / NAPT / Web 管理。

Web 不直接访问 `CanDriver`、`NagHandler` 或实时可变状态。

控制路径：

`Web → ControlCommand Queue/Mailbox → can_rt`

状态路径：

`can_rt → TelemetrySnapshot → Web 只读`

## 4. CAN 优先级模型

### S0：安全控制平面

S0 不属于普通 TX 队列，优先级高于所有业务。

触发条件包括：

- CAN Write OFF
- OTA 开始
- 软件重启
- driver shutdown
- Bus-Off
- 输入超时
- 连续输入校验失败
- 连续 TX 失败达到阈值

统一动作：

`关闭发送门 → 清理待发请求 → 等待当前发送结束或超时 → Listen Only / 必要时卸载 TWAI → TX 保持 recessive`

### P0：实时关键帧

当前：

- `0x370` Nag echo
- 后续若确有必要，可加入安全释放类实时帧

规则：

- 必须基于最新真实输入帧生成。
- 必须有绝对截止时间。
- 过期即丢弃，禁止发送旧帧。
- 同一 CAN ID 只保留最新一条待发请求。
- 不允许被 P1/P2 阻塞。
- 不做无期限重试。

### P1：普通控制帧

当前预留，无现有业务必须放入 P1。

规则：

- 有截止时间。
- 可在截止时间内有限重试。
- P0 到来时立即让路。

### P2：低优先级 CAN 发送

用于未来诊断、调试或测试类发送。

规则：

- 默认不主动发送。
- 仅 P0/P1 空闲时调度。
- 暂时延后不立即记为失败。
- S0、OTA、Bus-Off、输入异常期间全部暂停。

WiFi、DNS、日志和 WebUI 不进入 CAN TX 优先级队列。

## 5. 统一完整 CAN 链路

正式链路：

`真实 CAN 输入 → TWAI 硬件过滤 → RX 时间戳/序号 → ID/DLC 校验 → 输入 checksum 校验 → counter 连续性校验 → 新鲜度/周期校验 → 自发帧指纹排除 → 连续有效帧确认 → S0 安全状态 → 功能开关/门控 → 复制原始帧 → 仅修改允许字段 → torque 范围限制 → counter 生成 → checksum 重算 → 输出不变量复核 → TxRequest → P0/P1/P2 调度 → TWAI 入队 → TX 成功/失败事件 → Telemetry/Supervisor → 超时或故障回退`

### 5.1 输入有效性

对 `0x370` 至少检查：

- ID 精确匹配。
- DLC 必须满足协议长度。
- 输入 checksum 正确。
- counter 连续性合理。
- 接收时间在允许的新鲜度窗口内。
- 帧不是近期本机发出的 echo。

输入异常时不得继续基于旧模板生成发送帧。

### 5.2 连续有效帧确认

以下状态恢复后，不允许收到第一帧就立即恢复发送：

- 冷启动
- CAN Write OFF → ON
- Bus-Off 恢复
- TWAI 重装
- 输入超时后恢复
- OTA 中止后恢复

默认要求连续 2 个 checksum 正确、counter 合理、时间间隔合理的真实 `0x370` 帧后进入 ACTIVE。

具体时间阈值必须依据真实 `0x370` 周期确定，实施时不得凭空写死未经验证的毫秒值。

### 5.3 自发帧识别

替换当前仅比较 torque/counter/byte4 的方法。

使用短时间窗口内的 TX 指纹：

`CAN ID + DLC + 完整 payload + TX 时间`

只有完整匹配且处于允许时间窗的接收帧才视为本机 echo。

## 6. Supervisor 状态机

建议最小状态集：

- `BOOT`
- `LISTEN_ONLY`
- `ARMING`
- `ACTIVE`
- `STALE`
- `BUS_OFF`
- `DEGRADED`
- `OTA_QUIESCE`
- `SHUTDOWN`

核心转移：

`BOOT → LISTEN_ONLY → ARMING → ACTIVE`

任何 S0 条件可以从 ACTIVE/ARMING 进入安全状态。

`STALE` / `BUS_OFF` / `DEGRADED` 恢复后必须重新进入 `ARMING`，重新进行连续有效帧确认，不能直接回到 ACTIVE。

`SHUTDOWN` 必须幂等，进入后不得重新启用发送。

## 7. TX 调度与发送结果

### 7.1 TxRequest

业务模块不得直接调用 `driver.send()`，只能生成 `TxRequest`。

TxRequest 至少包含：

- `CanFrame frame`
- `priority`
- `created_at`
- `deadline`
- `source/feature`
- `replace_key`（例如 CAN ID）
- 必要的业务上下文 ID

### 7.2 队列规则

- P0 同 ID 新请求覆盖旧请求。
- 过期请求在进入 TWAI 前丢弃。
- P2 不得提前占满硬件 TX queue。
- 建议缩短 TWAI 硬件 TX queue，软件层控制优先级；目标值在实施阶段根据 ESP-IDF 行为和实际负载确定，优先考虑 4 而非当前 16。

### 7.3 结果分层

统计必须拆分：

- `generated`：业务生成 TxRequest。
- `enqueue_ok / enqueue_fail`：TWAI 入队结果。
- `tx_success / tx_failed`：驱动可获得的最终 TX 结果或告警事件。
- `expired / replaced / blocked`：软件调度结果。

Nag 的“已发送计数”不得在 `driver.send()` 前增加。

若 ESP-IDF legacy TWAI 无法提供逐帧严格 ACK 级关联，则必须明确记录能力边界：区分“TWAI 入队成功”和“控制器 TX success/failed 事件”，不得把入队成功命名为 ACK 成功。

## 8. 故障与恢复

### Bus-Off

- Supervisor 立即关闭业务发送。
- 清理过期 P0/P1/P2 请求。
- 执行驱动恢复。
- 恢复成功后进入 LISTEN_ONLY/ARMING。
- 连续有效真实帧确认后才回 ACTIVE。

### 输入超时

- 短超时：进入 STALE，停止生成新 TX。
- 长时间无有效输入：保持安全只读状态。
- 新输入恢复后必须经 ARMING。

时间值依据实车帧周期在实施阶段确定。

### TX 失败

Nag P0 失败后不反复重发旧 echo。

若下一真实帧已经到来：

`旧 TxRequest 作废 → 基于最新真实帧重新生成`

连续失败达到安全阈值时进入 DEGRADED/LISTEN_ONLY。

### OTA / Restart

保留 V1.0.3 现有设计：

- OTA 时停止业务发送。
- shutdown handler 统一安全退出。
- 等待短暂总线空闲。
- 停止/卸载 TWAI。
- TX GPIO 保持 recessive。

新的 Supervisor 只统一入口，不删除这些底层保护。

## 9. 模块边界

目标结构可按以下职责拆分，具体文件名允许实施时小范围调整：

```text
src/
├── app/
│   ├── app_runtime.cpp
│   └── system_state.cpp
├── can/
│   ├── can_runtime.cpp
│   ├── can_supervisor.cpp
│   ├── can_rx_validator.cpp
│   ├── can_tx_scheduler.cpp
│   ├── can_telemetry.cpp
│   └── twai_port.cpp
├── features/
│   └── nag/
│       ├── nag_codec.cpp
│       ├── nag_controller.cpp
│       └── nag_config.cpp
├── web/
│   ├── web_runtime.cpp
│   ├── web_can_api.cpp
│   └── web_wifi_api.cpp
└── main.cpp
```

职责：

- `TwaiPort`：只负责硬件，不知道 Nag。
- `CanRuntime`：独占 TwaiPort，执行统一链路。
- `CanSupervisor`：维护安全状态与恢复。
- `CanRxValidator`：输入合法性、新鲜度和连续确认。
- `NagController`：纯业务逻辑，输入真实帧与只读配置，输出可选 TxRequest。
- `CanTxScheduler`：优先级、deadline、replace、发送结果。
- `CanTelemetry`：生成跨核只读快照。
- `WebCanApi`：只发命令、读快照，不直接操作 driver/handler。

## 10. 并发模型

禁止 Web 和 CAN 通过普通全局变量直接共享可变状态。

控制配置采用单向命令：

`Web task → command mailbox/queue → can_rt`

状态采用单向快照：

`can_rt → atomic/versioned snapshot → Web`

Nag 模式、扭矩范围、CAN Write 等配置必须在 CAN 任务边界统一应用。

## 11. 保留与禁止修改

必须保留：

- 当前 `0x370` Nag 模式 A / A_V2 的业务行为和允许范围。
- 现有 counter+1 和 checksum 算法，除非验证发现协议实现错误。
- TWAI 500 kbit/s。
- 默认安全 Listen Only。
- CAN Write OFF 时硬件只读。
- 现有安全重启和 TX recessive 机制。
- WiFi AP+STA、NAPT、DNS、WebUI、手动 OTA 的产品行为。

本分支不做：

- 新增 FSD、自动换挡、灯光、速度偏移等其他车辆控制功能。
- 引入 MCP2515、SAME51、双路 CAN。
- 改 main 或其他禁止分支。
- 合并其他功能分支。
- 创建发布/源码运输工作流。

## 12. 测试设计（仅定义，不在当前确认前执行）

后续实施应新增/调整必要测试：

1. RX checksum/counter/新鲜度验证。
2. 连续两帧 ARMING → ACTIVE。
3. STALE/BUS_OFF/OTA/SHUTDOWN 禁止发送。
4. P0 覆盖旧同 ID 请求。
5. P0 deadline 过期丢弃。
6. P0 高于 P1/P2。
7. handler 不直接访问 CanDriver。
8. 发送计数只在明确结果阶段更新。
9. TX 指纹不误判普通真实帧。
10. Web command 与 telemetry snapshot 跨核边界。
11. 保留既有 Nag counter/checksum/torque/native 回归行为。
12. 保留既有 CAN restart safety 回归。

按照会话规则，在用户确认前不运行任何测试。

## 13. 验收标准

架构重建完成应满足：

1. CAN 实时任务独占 TWAI。
2. 业务模块不再直接发送 CAN。
3. 完整链路按统一顺序执行。
4. S0/P0/P1/P2 分层存在且职责明确。
5. P0 支持 deadline 和同 ID 最新帧覆盖。
6. Bus-Off/STALE/OTA/Restart 统一走 Supervisor 安全回退。
7. 恢复发送前必须重新进行连续有效帧确认。
8. Web 与 CAN 不再通过普通可变全局状态直接跨核耦合。
9. 发送统计区分 generated、enqueue 和 TX result。
10. 不改变现有 Nag 用户可感知行为。
11. 不修改 WiFi/DNS/NAPT/WebUI 产品功能。
12. 只修改本架构及必要测试，不跨功能扩张。
