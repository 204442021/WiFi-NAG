# WiFi-NAG V1.0.5 BLE 障碍物换挡设计

## 1. 状态与范围

- 目标分支：`V1.0.5`
- 基线分支：`V1.0.4`
- 本规格覆盖 WiFi-NAG 侧的 WebUI 卡片、BLE `BrakeState` 接收、CAN 过滤、`0x118` 采集与虚拟 P 挡注入、安全状态机、诊断和测试。
- T2CAN 侧负责生成权威刹车状态；WiFi-NAG 侧只消费该状态，并结合本机实时 `0x118` 决定是否发送虚拟 P 挡帧。
- 本规格不改变现有 NAG 算法、`0x255/0x12B` 障碍物转发语义、BLE 配对身份模型或现有 BLE 20 字节基础帧格式。

## 2. 目标

1. WebUI 中将 BLE 从现有配置区拆出，成为 NAG 大卡片下方的独立大卡片。
2. 在 BLE 大卡片下方增加“障碍物换挡”大卡片。
3. T2CAN 在真实挡位为 D/R、双源刹车有效且踩下、车辆静止等条件同时满足时，每 50 ms 向 WiFi-NAG 发送 `brakePressed=1`。
4. 条件失效时立即发送 `brakePressed=0`，随后以 50 ms 周期保持至少 500 ms。
5. WiFi-NAG 只有在本机收到新鲜的真实 `0x118` D/R 帧后，才按原帧实时生成虚拟 P 挡帧并发送，最长维持 500 ms。
6. 同一次踩刹车最多触发一次；只有收到明确的双源刹车释放确认后才能解锁下一轮。
7. 任一数据过期、BLE 断开、会话变化、挡位变化、车辆移动或发送失败都必须立即停止虚拟 P 挡发送并进入安全状态。

## 3. 硬件边界与发送语义

当前 WiFi-NAG 使用 ESP32-S3 单路原生 TWAI，只有一组 CAN RX/TX 引脚，不是双 CAN 的串联转发网关。因此固件不能物理阻断或替换车辆 ECU 已经发送到总线上的真实 `0x118`。

V1.0.5 的准确行为定义为：

```text
收到一帧真实 0x118 D/R
→ 保存真实原帧与真实挡位
→ 条件满足时，以这帧为模板生成一帧虚拟 P
→ 在同一 CAN 总线上紧随发送虚拟 P 帧
```

真实 `0x118` 和虚拟 P 帧会同时存在于同一总线上。这里的“修改原帧”是指复制刚收到的实时原帧、只修改指定字段并重新计算校验后注入，不是拦截并删除原车帧。

不允许使用固定录制帧、缓存帧周期重放或在结束时发送缓存的“恢复帧”。

## 4. WebUI 信息架构

主页面大卡片顺序固定为：

1. NAG
2. BLE
3. 障碍物换挡
4. 其余现有大卡片

### 4.1 BLE 大卡片

BLE 大卡片承接现有 BLE 子区块的全部能力：

- BLE 总开关与运行状态
- 扫描、连接、配对、绑定、解绑
- 本机与对端设备 ID、Boot ID、能力位、RSSI
- NAG 状态同步
- `0x255/0x12B` 障碍物数据状态
- 最近收发时间、重连/断连、CRC、长度、版本、未知类型、序列诊断

现有 DOM 控件 ID、API 路径和后端语义尽量保持不变，只改变静态归属和布局。

### 4.2 障碍物换挡大卡片

控制项：

- `D/R 挡启用换挡` 开关
- 第一次启动默认开启
- 用户修改后保存到 NVS，升级和重启后保留

状态项：

- 状态机：`WAIT_RELEASE / ARMED / ACTIVE_P / LATCHED`
- BLE：连接、协议就绪、对端是否支持 `BrakeState`
- BrakeState：值、原因、新鲜度、序列、发送端状态
- 双源刹车：物理刹车和系统刹车的 known/fresh/pressed、是否一致
- 释放确认：`releaseConfirmed`
- T2CAN 真实挡位、挡位新鲜度、静止确认、速度
- 本机真实 `0x118` 挡位、最后接收年龄
- 虚拟 P：是否发送、剩余时间、成功/失败次数
- 锁存：本次踩刹车是否已经触发
- 当前禁止或停止原因

## 5. CAN 接收过滤

### 5.1 条件归属

`0x118` 属于 BLE 障碍物换挡功能，不属于基础 NAG 功能。

- 未编译或未初始化 BLE 功能时：基础过滤器只需要 `0x370`。
- BLE 功能初始化后：BLE 有效过滤白名单为 `{0x370, 0x255, 0x12B, 0x118}`。
- 不能只修改 `NagHandler::filterIds()`；BLE 初始化完成后的二次过滤配置也必须包含 `0x118`，否则它会再次从软件精确白名单中消失。
- 推荐由 BLE 集成层维护唯一的有效 ID 列表，避免启动过滤器与 BLE 过滤器分别硬编码后再次不一致。

### 5.2 运行期行为

BLE 暂时断开、协议未就绪或用户关闭 BLE 时，不动态重装 TWAI 驱动来移除 `0x118`。此时：

- 继续允许 `0x118` 进入接收路径；
- 只更新真实挡位和新鲜度；
- 障碍物换挡状态机停止虚拟 P 并进入 `WAIT_RELEASE`；
- 不允许发送任何虚拟 P 帧。

保留现有驱动的软件精确白名单。硬件验收掩码可能同时放入额外 ID，但业务层只能接收四个显式 ID。

## 6. BLE 协议扩展

### 6.1 基础格式

继续使用现有 20 字节 BLE 包：

| 字节 | 内容 |
|---|---|
| 0 | Magic `0xA7` |
| 1 | 协议版本 `0x02` |
| 2 | Message Type |
| 3 | Message Flags |
| 4..7 | 全局 `uint32` 小端序列号 |
| 8..17 | 10 字节 Payload |
| 18..19 | CRC16-CCITT，小端；覆盖字节 0..17 |

新增消息：

```text
MSG_BRAKE_STATE = 0x12
方向：T2CAN → WiFi-NAG
```

新增能力位：

```text
CapabilityBrakeState = 0x10
kRequiredCaps         = 0x0F
kAdvertisedCaps       = 0x1F
```

握手仍只强制要求旧能力 `0x0F`。对端缺少 `0x10` 时，BLE 其他功能继续可用，只禁用障碍物换挡并显示“不支持 BrakeState”。

### 6.2 BrakeState Payload

| Payload | 定义 |
|---|---|
| P0 | Payload 版本，固定 `0x01` |
| P1 | 刹车标志 |
| P2 | 挡位与车辆标志 |
| P3 | 发送端状态标志 |
| P4 | 挡位来源 |
| P5 | 原因码 |
| P6..P7 | 刹车持续时间 ms，`uint16` 小端饱和值 |
| P8..P9 | 车速 × 0.1 km/h，`uint16` 小端饱和值 |

P1 刹车标志：

| Bit | 定义 |
|---|---|
| 0 | `brakePressed` |
| 1 | `releaseConfirmed` |
| 2 | physical known |
| 3 | physical fresh |
| 4 | physical pressed |
| 5 | system known |
| 6 | system fresh |
| 7 | system pressed |

P2 挡位与车辆标志：

| Bit | 定义 |
|---|---|
| 0..2 | `realGear`：0 unknown、1 P、2 R、3 N、4 D |
| 3 | gear fresh |
| 4 | brake sources agree |
| 5 | fallback active |
| 6 | speed fresh |
| 7 | stationary confirmed |

P3 发送端状态标志：

| Bit | 定义 |
|---|---|
| 0 | D/R confirmed |
| 1 | brake hold ready |
| 2 | active eligible |
| 3 | release tail |
| 4 | sender feature enabled |
| 5 | normal runtime |
| 6..7 | 保留，必须为 0 |

P4 挡位来源：

```text
0 = unknown
1 = 0x145
2 = 0x39D
```

P5 原因码：

| 值 | 名称 |
|---|---|
| `0x00` | IDLE/NONE |
| `0x01` | ACTIVE |
| `0x02` | RELEASE_CONFIRMED |
| `0x03` | BRAKE_STALE |
| `0x04` | BRAKE_CONFLICT |
| `0x05` | FALLBACK_ACTIVE |
| `0x06` | HOLD_PENDING |
| `0x07` | GEAR_UNKNOWN |
| `0x08` | GEAR_STALE |
| `0x09` | GEAR_NOT_DR |
| `0x0A` | SPEED_UNKNOWN |
| `0x0B` | SPEED_STALE |
| `0x0C` | VEHICLE_MOVING |
| `0x0D` | DISABLED |
| `0x0E` | SESSION_RESYNC |

未知 Payload 版本、保留位不为 0、字段组合自相矛盾或 CRC 错误的包不得驱动换挡状态机。

### 6.3 全局序列与会话

- BLE 序列号继续是所有消息共享的全局序列，不要求相邻两个 BrakeState 的序列连续。
- 使用 `uint32` 回绕安全的“是否更新”比较，只接受比最后接收包更新的序列。
- 重复包和旧包只计数，不刷新 BrakeState 新鲜度，也不改变状态机。
- 对端 Boot ID 变化、重新握手或新连接视为新会话：重置序列基线、清除旧 BrakeState，并进入 `WAIT_RELEASE`。

## 7. T2CAN 发送端状态机

### 7.1 ACTIVE 条件

以下条件必须全部满足：

- 功能开启且发送端处于正常运行态；
- 真实挡位已知、新鲜并确认为 D 或 R；
- 物理刹车与系统刹车均 known、fresh、pressed；
- 两路刹车信号一致；
- 未启用 fallback；
- 刹车连续保持至少 150 ms；
- 速度数据新鲜且车辆静止。

静止判定使用 `0x257`：

- 数据年龄不超过 300 ms；
- UI raw speed 为 0；
- DI speed valid；
- 解码绝对车速不超过 0.2 km/h。

满足条件时进入 `ACTIVE`：立即发送一次 `brakePressed=1`，之后每 50 ms 发送一次。

### 7.2 RELEASE_TAIL

检测到刹车释放或任一 ACTIVE 条件失效时：

1. 立即发送 `brakePressed=0`；
2. 随后每 50 ms 继续发送 `brakePressed=0`；
3. 从第一次 0 开始持续不少于 500 ms；
4. 时间点覆盖 0、50、100 … 500 ms，至少尝试 11 次；
5. 完成后进入 `IDLE` 并停止周期发送。

`releaseConfirmed` 语义必须独立于 `brakePressed`：

- 只有两路刹车均 known、fresh、一致且明确为 released，才能发送 `brakePressed=0 + releaseConfirmed=1`。
- 因 stale、conflict、fallback、挡位、速度、禁用或会话变化导致的停止，发送 `brakePressed=0 + releaseConfirmed=0`。
- 如果 RELEASE_TAIL 期间稍后得到明确释放确认，从该确认帧重新开始不少于 500 ms 的 `releaseConfirmed=1` 尾发。

重连或新会话后：

- 已明确释放：发送 0 + releaseConfirmed，保持不少于 500 ms；
- 仍满足 ACTIVE：发送 1；
- 未知、过期或冲突：发送 0 + releaseConfirmed=false。

## 8. WiFi-NAG 接收端状态机

### 8.1 状态

`WAIT_RELEASE`：启动、重启、BLE 断开、会话变化、BrakeState 过期或异常后的安全状态。忽略 `brakePressed=1`，只接受当前会话中新鲜的 `brakePressed=0 + releaseConfirmed=1` 进入 `ARMED`。

`ARMED`：等待一次新的有效踩刹车。收到新鲜有效的 `brakePressed=1` 后，还必须同时满足本机开关、BLE 能力、CAN Write、车辆静止以及本机实时 `0x118` D/R 条件，才可进入 `ACTIVE_P`。

`ACTIVE_P`：在最长 500 ms 的窗口内，根据每一帧新收到的真实 `0x118` 生成并发送虚拟 P。第一次成功发送虚拟 P 后立即锁存本次踩刹车。

`LATCHED`：本次踩刹车已经触发，忽略后续 `brakePressed=1`。只有当前会话中新鲜的 `brakePressed=0 + releaseConfirmed=1` 才解锁并回到 `ARMED`。

### 8.2 转移规则

```text
启动/重启/新 BLE 会话
→ WAIT_RELEASE

WAIT_RELEASE + 新鲜(0, releaseConfirmed=1)
→ ARMED

ARMED + 新鲜(1) + 全部本地安全条件
→ 等待下一帧实时 0x118 D/R
→ 首次虚拟 P 发送成功
→ ACTIVE_P，同时锁存

ACTIVE_P 达到 500 ms
→ 停止发送
→ LATCHED

ACTIVE_P 收到任意新鲜 brakePressed=0
→ 立即停止发送
→ 若 releaseConfirmed=1 则 ARMED，否则 LATCHED

LATCHED + 新鲜(0, releaseConfirmed=1)
→ ARMED
```

BrakeState 新鲜度阈值为 200 ms。超过阈值立即停止虚拟 P 并进入 `WAIT_RELEASE`，过期本身不能解除锁存。

同一次踩刹车无论收到多少个 `brakePressed=1`，最多产生一个 500 ms 虚拟 P 窗口。

## 9. 本机 0x118 处理

### 9.1 真实帧与新鲜度

- 只接受标准数据帧、ID `0x118`、DLC 8。
- 每次接收都保存完整真实原帧、真实接收时间和解析后的 `RealGear`。
- 真实帧对象永远不原地改写；UI、安全条件和状态机始终使用 `RealGear`，不能读取虚拟帧反推挡位。
- 本机 `0x118` 新鲜度阈值为 50 ms；正常样本周期约 10 ms。
- 只有接收到 `brakePressed=1` 之后到达的下一帧实时 `0x118` 才能启动窗口，禁止用触发前缓存的帧启动。

真实挡位编码：

```text
Byte2 = 0x32 → P
Byte2 = 0x55 → R
Byte2 = 0x95 → D
其他值       → unknown/other
```

### 9.2 虚拟 P 生成

以刚收到的真实 D/R 帧为模板：

```text
Byte2 = 0x32
Byte6 = 0x00
Byte1、Byte3、Byte4、Byte5、Byte7 保持原帧
Byte0 = (Byte1 + Byte2 + Byte3 + Byte4 + Byte5 + Byte6 + Byte7 + 0x19) & 0xFF
```

Byte1 的低四位滚动计数器直接继承当前实时原帧，不自行生成或重放。

示例：

```text
D: 0F 61 95 30 00 C8 08 00
P: A4 61 32 30 00 C8 00 00

R: DC 6E 55 30 00 C8 08 00
P: B1 6E 32 30 00 C8 00 00
```

对用户提供的 7652 帧样本分析结果：P 挡 Byte2 固定为 `0x32`、Byte6 固定为 `0x00`，校验公式在全部样本中成立。D/R 按上述规则转换后的其余字段组合约 88.5% 能在实测 P 帧中直接找到，约 11.5% 是样本中未出现过的字段组合。因此该规则是 V1.0.5 的第一阶段候选，必须经过台架/实车受控验证；不得为了追求样本命中率而硬编码 Byte3 或 Byte5。

### 9.3 发送窗口

- 在 `ACTIVE_P` 中，每收到一帧新的实时 D/R `0x118`，发送一帧由它生成的虚拟 P。
- 500 ms 从第一帧虚拟 P 成功写入 CAN 驱动时开始计时。
- 发送失败不允许把失败帧缓存后重放；立即停止并进入安全状态。
- 窗口结束时不发送缓存的“恢复 D/R”帧；后续真实车辆帧自然继续存在于总线上。

### 9.4 立即停止条件

任一条件成立都立即停止虚拟 P：

- 收到新鲜 `brakePressed=0`；
- BrakeState 超过 200 ms；
- BLE 断开、协议失去 ready、对端 Boot ID 或会话变化；
- 本机 `0x118` 超过 50 ms；
- 本机真实挡位离开 D/R 或无法识别；
- 车辆不再静止或速度状态无效；
- 对端缺少 `CapabilityBrakeState`；
- 障碍物换挡开关关闭；
- BLE 总功能关闭；
- CAN Write 关闭、CAN 不在线、OTA/重启准备开始；
- CAN 写入失败；
- 设备重启或状态机检测到字段矛盾。

除明确收到 `releaseConfirmed=1` 外，上述停止均不能自动解锁下一次触发。

## 10. 并发与隔离

- BLE 任务只负责校验并发布不可变的最新 BrakeState 快照，不直接发送 CAN。
- CAN 任务是 `0x118` 真实帧、状态机转移和虚拟 P 发送的唯一写入者，避免 BLE 回调与 CAN 快速路径同时修改状态。
- WebUI 只读取诊断快照并提交持久化开关，不直接改变状态机内部字段。
- 现有单个 `onFrame` 回调需要保留 dashboard 与 `0x255/0x12B` 观察能力，并把 `0x118` 路由到独立换挡控制器；不能用新的回调覆盖现有观察器。
- 虚拟 P 自发帧必须有独立指纹/计数，防止被接收回环误认为新的真实 `0x118`。

## 11. 错误处理与安全默认值

- 第一次启动只有 UI 功能开关默认开启；状态机仍从 `WAIT_RELEASE` 开始，不能因默认开启直接发帧。
- 任何 unknown、stale、conflict、缺失能力或解析失败都按“不允许发送”处理。
- BLE 缺少新能力只禁用障碍物换挡，不得让旧 BLE 功能整体进入 incompatible。
- 重启、OTA、CAN 重装和写模式切换前先清除 ACTIVE 窗口并阻止新触发。
- 诊断计数器只能帮助定位问题，不能作为解除锁存或绕过新鲜度的依据。

## 12. 测试设计

### 12.1 BLE 协议测试

- `0x12` 被识别为合法消息类型。
- Payload 位、版本、原因码、大小端和 CRC 往返正确。
- `kRequiredCaps=0x0F`、`kAdvertisedCaps=0x1F`；缺少 `0x10` 不影响旧功能握手。
- 全局序列允许其他消息造成间隔，拒绝重复和旧序列，并覆盖 `uint32` 回绕。
- 新连接和 Boot ID 变化重置序列基线并进入 `WAIT_RELEASE`。

### 12.2 过滤器测试

- BLE 未启用时基础列表只有 `0x370`。
- BLE 初始化后的精确白名单包含且只包含 `0x370/0x255/0x12B/0x118`。
- 四个目标 ID 全部通过软件精确过滤；相邻和无关 ID 被拒绝。
- 后置 BLE 过滤配置不会把启动阶段加入的 `0x118` 再次移除。
- BLE 断连不会触发 TWAI 动态重装。

### 12.3 T2CAN 合同测试

- ACTIVE 首帧立即发送 1，之后严格按 50 ms 周期。
- 所有 ACTIVE 条件均有单独失效测试。
- RELEASE_TAIL 在 0..500 ms 至少发送 11 次 0。
- 普通失效为 `releaseConfirmed=0`；双源明确释放为 1。
- 尾发期间迟到的释放确认会重新启动 500 ms 确认尾发。

### 12.4 WiFi-NAG 状态机测试

- 启动和新会话必须先收到明确释放才能 ARMED。
- WAIT_RELEASE 忽略所有 1。
- 同一次踩刹车只触发一次。
- 200 ms BrakeState 过期和 50 ms `0x118` 过期立即停止且不能解锁。
- ACTIVE_P 中任意新鲜 0 立即停止；只有 releaseConfirmed 才解锁。
- 所有停止条件均覆盖状态和诊断原因。

### 12.5 0x118 测试

- D、R、P 和未知挡位解析。
- D/R 示例转换结果与校验值完全匹配。
- 保留 Byte1/3/4/5/7，修改 Byte2/6，重算 Byte0。
- 每一帧虚拟 P 使用对应的最新实时原帧，不使用固定帧或旧缓存。
- 500 ms 从首次成功发送开始，结束后不发送恢复帧。
- 自发回环不能更新 RealFrame 或延长 ACTIVE_P。
- CAN Write 关闭和发送失败均不产生重试重放。

### 12.6 WebUI 与构建验收

- 大卡片顺序为 NAG → BLE → 障碍物换挡。
- BLE 原控件与 API 无回归。
- 换挡开关默认开启、NVS 持久化，状态和原因可实时显示。
- 页面源文件和生成的 gzip 产物同步。
- Python 回归测试、native PlatformIO 测试和 ESP32-S3 正式固件构建全部通过。

## 13. 设备级验收

在受控台架或封闭场地完成，不能以静态测试替代：

1. 确认实际总线上 `0x118` 周期、D/R/P 编码、计数器和校验与样本一致。
2. 确认同一总线上真实 D/R 与注入 P 并存时，目标控制器的实际选择行为符合预期。
3. 确认首次有效踩刹车只触发一次，500 ms 后停止，持续踩住不会再次触发。
4. 确认双源明确释放后可进行下一轮。
5. 逐项拔掉 BLE、制造数据过期、改变挡位、让车辆移动、关闭开关和关闭 CAN Write，确认都能立即停止。
6. 若目标控制器不能稳定接受同总线的注入 P，V1.0.5 不得宣称该功能完成；需要重新评估硬件拓扑或仲裁策略。

## 14. 完成标准

- 规格中的 BLE 合同由 T2CAN 与 WiFi-NAG 两端一致实现。
- `0x118` 只随 BLE 功能加入有效过滤列表，不污染无 BLE 的基础 NAG 配置。
- 所有安全门、新鲜度、锁存和释放确认测试通过。
- WebUI 布局、持久化和诊断完整。
- 正式固件构建通过，并完成设备级受控验证。
- 在设备级验证通过前，功能在 UI 中必须明确标记为测试功能，不能视为道路安全功能。
